# GlowMatch — System Design (HLD + LLD)

## High-Level Design (HLD)

### The big picture

```
                        ┌─────────────────────┐
                        │   Client (browser,      │
                        │   Postman, mobile app)   │
                        └───────────┬─────────────┘
                                    │  HTTP requests
                                    ▼
                        ┌─────────────────────┐
                        │   FastAPI Service        │
                        │   (src/api.py)             │
                        │   - async request handlers  │
                        │   - Pydantic validation      │
                        └───────┬───────────┬────────┘
                                │           │
                    cache check │           │  cache miss →
                                ▼           ▼  compute + store
                        ┌───────────┐  ┌────────────────────┐
                        │   Cache      │  │  Recommender Engine   │
                        │   (Redis, or │  │  (src/recommender.py)   │
                        │   in-memory  │  │  - TF-IDF content model  │
                        │   fallback)   │  │  - LSA vector embeddings  │
                        └───────────┘  │  - Nearest-neighbor index  │
                                        │  - KMeans personas          │
                                        │  - Rule-based personalization │
                                        │  - Mini-RAG explanations       │
                                        └────────┬───────────────────┘
                                                 │
                                                 ▼
                                        ┌─────────────────────┐
                                        │  Data Layer               │
                                        │  cosmetics.csv (today)     │
                                        │  → MongoDB (production)      │
                                        └─────────────────────┘
```

### Component responsibilities

| Component | Responsibility |
|---|---|
| **FastAPI service** | Exposes recommendation logic over HTTP; validates requests; handles concurrency via `async def` |
| **Cache layer** | Serves repeated identical queries near-instantly; protects the compute-heavy engine from redundant work |
| **Recommender engine** | All the actual ML: content similarity, vector search, personalization, clustering, explanation generation |
| **Data layer** | Source of truth for the product catalog (a CSV today; a real production system would use MongoDB — see below) |

### Why MongoDB in production (not in this submission)

This assignment's catalog is small and static (1,472 rows), so a CSV is
appropriate and keeps the submission simple to run with zero setup. In a
real BeautyTech platform, the catalog would live in **MongoDB** because:
- Product schemas vary by category (a sunscreen has an SPF field a
  moisturizer doesn't) — MongoDB's schema-flexible documents handle this
  naturally, unlike a rigid SQL table.
- Product data updates frequently (new arrivals, price changes, restocks)
  — a document database handles high-frequency partial updates well.
- This directly matches the JD's required skill (**MongoDB / NoSQL**).

### Why Redis in production

Recommendation queries repeat heavily in real traffic (many users share
the same skin type + category combination). Caching those results in
Redis means the expensive computation (TF-IDF similarity, nearest-neighbor
search) runs once per unique query, not once per request — this is
exactly what the cache-hit/cache-miss latency numbers in `TEST_CASES.md`
demonstrate (63ms → 0.04ms on a repeated query).

### Why async FastAPI

A synchronous API can only process one request at a time per worker —
if 100 users hit `/recommend` simultaneously, request #100 waits for 99
others to fully finish. `async def` lets FastAPI's event loop juggle many
in-flight requests concurrently (especially valuable once real I/O like a
database call or cache round-trip is involved), which is the standard
pattern for production Python APIs at any real scale.

## Low-Level Design (LLD)

### API Contract

| Endpoint | Method | Query Params | Returns |
|---|---|---|---|
| `/recommend` | GET | `skin_type` (required), `category`, `max_price`, `n` | List of products matching skin-type flag, ranked by rating |
| `/similar` | GET | `product_id` (required), `n` | List of products blending content + vector-search similarity |
| `/trending` | GET | `category`, `n` | Top-rated products, optionally filtered |
| `/explain` | GET | `query_product_id`, `recommended_product_id` | Mini-RAG grounded explanation string |

Full interactive contract (auto-generated by FastAPI from the Pydantic
models in `src/api.py`) is available at `/docs` when the server is running.

### Response schema (`Product`)

```json
{
  "product_id": 244,
  "Brand": "LANEIGE",
  "Name": "Water Bank Dual Layer Face Oil",
  "Label": "Moisturizer",
  "Price": 38.0,
  "Rank": 5.0,
  "match_score": null
}
```

### Cache key design

Cache keys are built as `{endpoint}:{param1}:{param2}:...` — e.g.
`recommend:Dry:Moisturizer:50:10`. This means two requests are only ever
treated as "the same" if every parameter matches exactly, which is the
correct cache-invalidation granularity for this use case (no risk of
serving a Dry-skin user an Oily-skin cached result).

### Fallback design (a real engineering decision, not an accident)

`src/api.py` attempts a real Redis connection at startup
(`_connect_cache()`), and **falls back to an in-memory Python dict with
the identical get/set interface** if no Redis server is reachable. This
means:
- The exact same code path (cache-check → cache-set) is exercised whether
  or not Redis is actually installed.
- The submission runs with zero infrastructure setup (no Docker, no
  Redis install required) while still correctly demonstrating the caching
  pattern.
- In a real deployment, pointing `REDIS_HOST`/`REDIS_PORT` at a managed
  Redis instance (e.g. GCP Memorystore) requires no code changes — only
  configuration.

### Concurrency model

Each endpoint is declared `async def`. The recommender engine's actual
computation (`recommend_for_skin_profile`, etc.) is CPU-bound pandas/numpy
work, so it doesn't natively benefit from `async` the way I/O-bound work
would — but the **cache layer round-trip and the API layer itself** are
where async concurrency matters, and the endpoints are structured so that
swapping the in-memory fallback for real async Redis calls
(`redis.asyncio`) or adding a real database call later requires no
architectural change.
